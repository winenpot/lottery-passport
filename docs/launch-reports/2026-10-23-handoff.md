## 5. Leaderboard design (summary; details land with the code)

- Domain (`app/domain/leaderboards.py`, framework-free): a board definition = id, metric,
  direction (`lower_is_better` for reaction time), periods (`today`/`week`/`all`, Tehran
  calendar via `app/domain/periods.py`), rule "each player's best in the window, ties to
  whoever set it first". A code registry of boards; Tap Reflex is the first entry.
- Application: a `LeaderboardReader` port (top N, my rank) and a service with a 60 s
  in-process cache (ADR 0004: no Redis).
- Infrastructure: one PostgreSQL query per *source kind* (first: accepted
  `mini_game_runs`, best `average_reaction_ms`); weekly coins (B21) becomes a second
  source over the ledger, with no new endpoint shape.
- API: `GET /api/v1/leaderboards/mini-games/{mini_game_id}?period=` as already specified
  in `docs/API_CONTRACT.md`, plus `direction`/`unit` so the client can render ms.
  `features.leaderboard` stays false until Arman's screen is ready.
- **No migration** in the first version (17 runs; existing `ix_mini_game_runs_user_status`
  is enough). An index comes later, additive and `CONCURRENTLY`, once volume is measured.
